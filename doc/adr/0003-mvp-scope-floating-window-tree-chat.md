# ADR-0003: MVP (v1) scope limited to floating window + tree chat; screen awareness and study sessions phased

**Status:** `accepted`
**Date:** `2026-10-02`
**Deciders:** `产品所有者（本人）`

## Context

产品规划包含五组功能：1) 边缘吸附悬浮窗；2) 屏幕感知与选中即问；3) 树状对话（子对话/书签/链路图）；4) 学习会话（开始/暂停/结束学习、纪要式总结、出题检验）；5) 学习暂停。各功能的技术风险与依赖关系不同：树状对话是纯前端 + SQLite 工作，无不确定技术，且是市面上几乎没有竞品的差异化功能；屏幕感知在 ADR-0002 核实 deepseek-flash 视觉能力后从研究风险降为工程问题，但仍涉及触发方式、截图范围、上下文组装、延迟等交互设计迭代；学习会话依赖屏幕感知的输出作为输入，无法先行。一次全量开发会导致交付周期过长且各功能互相拖累。

## Decision

We will 按三期交付：

- **v1（MVP）**：悬浮窗（边缘吸附、分屏）+ 完整树状对话（主/子/子子对话、选中 AI 输出内容开子对话、对话书签、树状侧栏与单对话链路图、按科目分类的多对话存档）+ API 对话 + 教学系统提示词初版。
- **v2**：屏幕感知（截图提问、选中即问），基于 deepseek-flash 视觉能力的纯工程实现。
- **v3**：学习会话（开始/暂停/结束学习、纪要模板总结、思维导图、出题检验、知识画像）。

## Consequences

- 正面：v1 约 2-3 周即可交付并独立解决"查资料打断学习"与"长对话逻辑混乱"两个真实痛点；树状对话这一差异化功能最快接受真实使用检验；v2、v3 排期从"未知"变为可估计。
- 负面：用户最期待的屏幕感知要晚一个版本才能用上；v1 期间需继续忍受现有网页版 AI 的屏幕信息割裂问题。
- 中性：若 v1 实际使用中发现排序判断有误，可在 v1 复盘时调整 v2/v3 边界。

## Alternatives Considered

* 全量一次开发 — 周期约三个月，交付时任何设计误判都已固化，返工成本高。
* 屏幕感知进 v1 — 交互设计迭代会拖慢树状对话交付，两边都做不稳；deepseek-flash 视觉能力核实后曾重新评估，仍维持分期。
* 学习会话先行 — 其输入依赖屏幕感知，依赖顺序不成立。
