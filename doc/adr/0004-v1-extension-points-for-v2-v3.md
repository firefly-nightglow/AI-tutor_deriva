# ADR-0004: v1 为 v2/v3 预留的三个扩展点

**Status:** `accepted`
**Date:** `2026-10-02`
**Deciders:** `产品所有者（本人）`

## Context

开工 v1 前，产品所有者提出担忧：直接搭建 v1 可能给 v2（屏幕感知）、v3（学习会话）的后续建设造成返工。分析表明返工风险不来自缺少 v2/v3 文档（详细规格在有 v1 使用经验前编写只会是臆测，PRD Roadmap 已在功能粒度锚定其范围），而来自 v1 中少数几个做错即卡住 v2/v3 的接口。逐一排查后确认真正的卡点有三个：消息表不支持图片附件与特殊内容类型（v2 截图消息、v3 纪要/思维导图需要）；LLM 调用的上下文组装若写死，v2 注入截图、v3 注入知识画像时都要改动核心；v2 屏幕捕获与 v3 会话状态机都需要在 Electron 主进程中有明确的模块归属。其余 v2/v3 要素（学习会话表、知识画像表、概念节点）均为纯增量新表，无返工风险，当前不预留。

## Decision

We will 在 v1 实现中预留三个扩展点，且不编写 v2/v3 的功能规格与任务（待 v1 使用经验积累后按 /ad-spec 流程再写）：

1. **消息表预留字段**：messages 表包含 content_type（默认 text）与 attachments（JSON，默认可为空），v1 不使用但不删除。
2. **上下文组装管线**：LLM 调用的上下文组装实现为"system prompt -> 可插拔 context blocks -> 对话链"的管线结构，v1 仅实现对话链一种 block，接口允许后续注入截图与知识画像。
3. **主进程模块边界**：主进程按 db / llm / capture / session 划分模块目录，capture 与 session 在 v1 为占位空模块。

## Consequences

- 正面：v2 截图消息与 v3 特殊内容无需数据迁移即可入库；v2/v3 的上下文注入不改动 LLM 调用核心；主进程新增能力有明确归属，不会长成单体。三项预留总成本约半小时。
- 负面：v1 代码中存在少量"现在不用"的字段与空目录，需要本 ADR 解释其存在理由。
- 中性：若 v2/v3 实际需求与预留接口不符，修改预留的成本与现在不预留相近——预留是低成本的保险，不是承诺。

## Alternatives Considered

* 开工前完整编写 v2/v3 规格与任务 — v1 使用经验会改写 v2/v3 的交互设计，现在写出的详细规格大概率返工；且违反"规格不写臆造值"的文档纪律。
* 不做任何预留直接开工 — 三个接口卡点中至少消息表结构一处几乎必然返工（含数据迁移）。
