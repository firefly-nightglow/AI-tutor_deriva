# Spec 0004: 外部应用并排（External App Tiling）

**Status:** `accepted`
**Created:** `2026-10-18`
**Owner:** `产品所有者（本人）`

## Context

SPEC-0003 用 Deriva 内嵌资料面板解决网页、PDF、视频网站和普通文件的同屏阅读，但它无法承载用户自己的 VSCode 工程、带扩展与登录态的浏览器、B 站桌面客户端等原生应用。产品所有者在 Task 0017 验收后确认：只做内嵌面板仍会回到“在 Deriva 与学习软件之间来回切换”的痛点，因此把“选择一个外部应用，与 Deriva 抽屉自动并排、共享工作区”作为 v2 的独立规格。

本规格只管理**外部应用的窗口几何**：枚举窗口、移动/缩放、暂停与还原。它不读取外部应用画面、不注入脚本、不模拟点击、不采集音频。屏幕与音频采集属于 v3 的学习会话，本规格只预留稳定的窗口/进程标识供其复用。

术语沿用 CONTEXT.md：悬浮抽屉、快捷气泡、并排应用、内嵌分屏、学习会话。技术路径见 ADR-0006 与 ADR-0009。

## User Scenarios

- **Scenario 1：选择 VSCode 并排**
  - Given Deriva 以悬浮抽屉运行，用户正在 VSCode 中写代码
  - When 用户点击“选择并排应用”，从窗口列表中选择 VSCode
  - Then VSCode 自动移到 Deriva 所在的显示器，与抽屉左右并排，双方都铺满工作区高度；Deriva 仍保持焦点

- **Scenario 2：调整边界**
  - Given Deriva 与 VSCode 已并排
  - When 用户拖动抽屉内侧边界
  - Then 两侧窗口同步调整宽度，边界变化受最小宽度约束；松手后记住比例

- **Scenario 3：收起与展开**
  - Given 外部应用正在并排
  - When 用户收起 Deriva、切回普通窗口或正常退出
  - Then 外部应用恢复到开始并排前的位置、大小、最大化状态与显示器；Deriva 重新展开时自动恢复并排

- **Scenario 4：应用关闭或无法控制**
  - Given 用户选择的应用已关闭、最小化、以管理员权限运行或被系统保护
  - When 应用尝试并排
  - Then 显示可理解的失败原因与手动处理建议，不留下只移动了一半的窗口；Deriva 对话区保持可用

- **Scenario 5：多显示器与显示器移除**
  - Given 并排应用与 Deriva 位于同一显示器
  - When 用户把抽屉移到另一显示器，或该显示器被断开
  - Then 应用跟随到新显示器并重新并排；显示器消失时先还原应用，再停止并排，不把窗口留在屏幕外

- **Scenario 6：异常退出后的还原**
  - Given Deriva 在并排期间崩溃或被强制结束
  - When Deriva 下次启动
  - Then 若被并排应用仍在运行，提示用户或自动还原其原始窗口状态；不得静默丢失还原记录

## Requirements

### Functional

- FR-1: Deriva 提供“选择并排应用”入口与窗口选择器。选择器列出当前可控制、可见的顶层窗口，排除 Deriva 自身窗口、系统外壳窗口、不可见/被隐藏窗口与已失效窗口；同一应用有多个窗口时以窗口为单位选择，而不是只按进程选择。
- FR-2: 同一时间只允许一个外部应用处于并排状态。选择新应用时先还原旧应用，再进入新的并排。
- FR-3: 并排时，Deriva 抽屉保持在用户选定的左/右边缘；外部应用占据剩余工作区，高度等于工作区高度。两侧不得重叠，任务栏区域不得被覆盖。
- FR-4: 用户可拖动抽屉内侧边界调整两侧宽度；拖动过程中两侧窗口同步更新，松手后持久化比例。两侧各自有最小宽度，低于最小值时停止继续拖动并给出视觉反馈。
- FR-5: 并排是“按用户选择摆放一次并保持”的能力，不是持续强制锁定。用户手动移动或缩放被并排应用后，Deriva 解除并排状态，保留应用选择并显示“重新并排”入口，不强行把窗口拉回。
- FR-6: 抽屉收起成气泡、切换回普通窗口或正常退出时，暂停并排并还原外部应用在开始并排前的 bounds、最大化状态与所在显示器；在同一次运行会话内重新展开抽屉时，若选择仍有效则自动恢复并排。应用重启后的恢复不适用本条，按 FR-12 处理。
- FR-7: 被并排应用关闭、崩溃或窗口句柄失效时，解除并排、清除失效选择并提示重新选择；对话数据不受影响。
- FR-8: 应用以管理员权限运行、受系统保护或拒绝窗口调整时，显示“无法控制该窗口”的具体原因，并提供手动使用 Windows 贴靠的操作说明；不得尝试提权或注入。
- FR-9: 多显示器下，并排发生在 Deriva 抽屉当前所在的显示器。抽屉跨显示器移动后，外部应用跟随并重新并排；显示器移除时先还原应用，再停止并排。
- FR-10: 应用维护“待还原”记录，包含窗口标识、原始 bounds、最大化状态与显示器。Deriva 正常退出时立即还原并清除记录；异常退出后下次启动检测残留记录，按开放问题的决议处理。
- FR-11: Deriva 界面显示当前并排应用、并排状态（生效/暂停/失败）以及“更换 / 重新并排 / 停止并排”入口。
- FR-12: 并排选择与比例按显示器持久化，重启后不自动静默接管外部窗口；必须由用户显式确认（例如点击“恢复并排”）后才恢复并排。启动时抽屉已展开不视为确认。
- FR-13: 本规格只调用窗口几何相关能力（枚举、读取 bounds、设置位置/大小、还原/最大化状态），不得读取窗口内容、注入代码、模拟输入或绕过应用自身的最小尺寸限制。
- FR-14: 向 v3 暴露稳定的窗口/进程标识与当前 bounds 查询接口，供后续屏幕捕获或进程音频采集复用；本规格不实现任何采集或总结。

### Non-functional

- NFR-1: Windows 原生窗口控制必须封装在独立适配器中，并由主进程管理的专用 Electron utility process 执行；主进程只持有异步 service proxy、生命周期与类型安全 IPC。渲染进程不得直接持有窗口句柄或调用原生 API。
- NFR-2: 坐标换算必须正确处理多显示器、DPI 缩放、工作区与物理像素差异；不得因缩放比例变化把窗口移到错误显示器或屏幕外。
- NFR-3: 边界拖动与窗口移动不得阻塞主进程事件循环或流式回答；连续拖动时合并高频更新，避免明显闪烁和卡顿。
- NFR-4: 任何原生调用失败都必须被捕获并转化为可理解的状态，不得导致 Deriva 崩溃；失败时优先还原已移动的窗口。
- NFR-5: “待还原”记录保存在本地用户数据目录，权限最小化，不写入日志；窗口标题可能包含敏感信息，不得原样写入日志或上传。
- NFR-6: 窗口选择器、边界拖动条、停止/重新并排控件在 Windows 触屏设备上可用，点击热区不小于 44px。
- NFR-7: 窗口选择器必须可用键盘操作，并提供窗口标题、应用名与当前状态，避免只靠图标识别。
- NFR-8: 打包后不得要求用户单独安装编译器；原生依赖的安装、升级与卸载路径必须在 spike 中验证并记录。

## Success Criteria

- 用户能在 VSCode、Chrome 与 B 站桌面客户端中至少各完成一次“选择 → 并排 → 调整边界 → 收起还原 → 重新展开恢复并排”的完整流程。
- 并排后两侧窗口不重叠、不覆盖任务栏，Deriva 仍可正常输入与流式回答。
- 用户手动移动被并排应用后，Deriva 解除并排且不会强行拉回；用户可一键重新并排。
- 关闭应用、管理员权限应用、显示器移除与 Deriva 正常退出时，窗口都能回到合法状态或有明确的手动恢复说明。
- 重启 Deriva 后不会静默接管外部窗口；用户展开抽屉或确认后才恢复并排。
- 全流程不读取外部应用内容、不注入代码、不模拟输入；日志中不出现完整窗口标题。

## Edge Cases

- 目标窗口已最小化、最大化、全屏、位于其他虚拟桌面、无标题、尺寸为零或正在关闭。
- 目标应用以管理员权限运行，或 Deriva 自身以不同权限级别运行。
- 目标应用有最小宽度限制，无法压缩到用户拖动的边界。
- 用户在并排期间手动移动、缩放、最大化或最小化目标应用。
- 用户在并排期间关闭目标应用、重启资源管理器或切换虚拟桌面。
- Deriva 抽屉跨显示器移动、显示器被拔出、分辨率或 DPI 改变。
- 并排期间 Deriva 崩溃、被强制结束或断电，残留“待还原”记录。
- 目标应用自身弹出模态窗口或登录窗口，主窗口句柄发生变化。
- 用户连续快速更换并排应用，旧应用的还原与新应用的并排发生竞态。

## Out of Scope

- 读取外部应用画面、OCR、视觉理解、字幕提取、音频采集与实时总结（v3）。
- 向外部应用注入脚本、模拟点击/键盘、读取其内部 DOM 或无障碍树。
- 同时并排两个以上外部应用，或把多个应用组成一个布局。
- macOS / Linux 的窗口控制；v2 仅承诺 Windows。
- 为特定应用编写插件或深度集成。
- 绕过管理员权限、UIPI、DRM 或应用自身的窗口限制。

## Spike Gate

正式实现前必须先完成 `/ad-ground` 四源调研（`doc/research/0016-ground-external-app-tiling.md`、`doc/research/0018-ground-external-app-tiling-production.md`）与 Task 0021 的 Windows 窗口控制 spike（`doc/research/0017-spike-external-app-tiling.md`）。spike 至少覆盖：

1. 枚举 VSCode、Chrome、B 站客户端的顶层窗口，拿到稳定标识、bounds 与最大化状态。
2. 对三者分别完成并排、边界调整、还原，并验证 DPI 缩放与多显示器场景。
3. 验证管理员权限窗口的失败表现与降级提示。
4. 验证所选技术（优先评估 `koffi` 调用 `user32`，备选原生 addon）在开发环境与打包后的可用性。

spike 未通过时，本规格不进入正式实现；v2 仍交付 SPEC-0003 的内嵌资料面板。

## Open Questions

- **OQ-1：窗口选择器列出当前显示器窗口，还是所有显示器窗口？**

  倾向：默认列出所有显示器上的可见窗口，选中后把应用移动到 Deriva 所在显示器；提供“仅当前显示器”过滤。
- **OQ-2：两侧最小宽度取多少？**

  倾向：Deriva 抽屉沿用 360px 下限；外部应用默认最小 480px，若工作区不足则按比例缩小并提示。
- **OQ-3：用户手动移动被并排应用后，解除并排还是自动拉回？**

  决议（2026-10-18）：解除并排，保留选择并提供“重新并排”，不强行拉回。
- **OQ-4：异常退出后的待还原记录，下次启动自动还原还是询问？**

  倾向：先检测应用是否仍在运行；若仍在运行则询问用户，避免启动时静默移动别人的窗口。
- **OQ-5：窗口图标是否必须？**

  倾向：首版用应用名 + 窗口标题 + 图标（可取则取），图标缺失不影响选择。
- **OQ-6：UWP 应用是否纳入首版？**

  倾向：不做专门适配；能通过普通顶层窗口枚举与移动就支持，失败则按 FR-8 降级。

## V3 Extension Points

- 并排应用保存稳定的窗口标识与进程标识，v3 可复用为屏幕捕获或进程音频采集的来源，但 v3 不得假设并排始终处于生效状态。
- v3 的屏幕读取必须排除 Deriva 的主抽屉、快捷气泡、截图遮罩与内部资料面板窗口，并按目标窗口当前 bounds 动态解析区域。
- v3 的“实时总结要点”按两条独立来源接入同一学习会话：屏幕内容与音频转写。本规格不决定两者的实现顺序、采样频率、模型或本地/云端方案。
